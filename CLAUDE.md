# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

**Maker Map** — a static, client-side web app for managing map areas and exporting presentation images. There is **no build step, no test suite, no package.json**, and exactly **one piece of server code** (`netlify/functions/isocrona.mjs`, which exists only to hold an API key out of the public page). The entire product is served as-is:

- `index.html` — login/signup landing page (the entry point).
- `app.html` — the map tool itself (~6,400 lines, everything inline: HTML + CSS + JS).
- `logo-makermap.png` — brand logo, referenced by `<img src="logo-makermap.png">` in both pages.
- `censo/` — IBGE 2022 census data, **one file per state** (`35.json` = SP, 98,989 sectors, 1.40 MB gzipped; `31.json` = MG, 49,924, 0.74 MB; `29.json` = BA, 30,311, 0.44 MB) plus `censo/manifest.json` listing what exists and each state's bounding box. **Fetched lazily**, and only for the states the current radius reaches. Not code — data.
- `netlify.toml` — deploy config (`publish = "."`; its `command` only strips `*.md` and `tools/` from the published output).
- `netlify/functions/ipca.mjs` — fetches **BCB SGS series 433** server-side and returns the array **unaltered**, so the client changed only its URL; the parsing, the target month and the no-invented-index rule stay in `app.html`. It exists because the browser-side call fails for some visitors (CORS, flaky networks) and the panel then shows uncorrected July/2022 money. `carregarIPCA()` tries `/api/ipca` **first and falls back to the direct BCB call**, deliberately: the two ends fail for opposite reasons — our endpoint egresses from cloud IPs abroad, which Brazilian public services sometimes refuse, while the browser has a residential Brazilian IP but is subject to CORS. A **truncated but 200** series gets a 10-minute CDN TTL instead of six hours, so a momentarily short series is not cached as if it were complete; `stale-if-error` serves the last **real** series when BCB is down. Errors carry **no** cache header.
- `netlify/functions/isocrona.mjs` — the first piece of server code. Proxies the OpenRouteService isochrone API so that `ORS_API_KEY` (a Netlify environment variable) never reaches the browser. Zero dependencies, by design: the repo has no `package.json`, and a 100-line endpoint is not a reason to introduce the first build step. Served at `/api/isocrona` via its own `config.path`.
    - **`publish = "."` would serve the function's own source** at `/netlify/functions/isocrona.mjs`. The key isn't in the code, so it's not a credential leak, but it hands out the validation logic. This cannot be fixed with `rm -rf ./netlify` in `command` the way `tools/` was — the command runs *before* function bundling and would delete the function. A `[[redirects]]` rule 404s `/netlify/*` instead. **Verify that 404 on the published site after any deploy that touches this.**
    - The endpoint is **public**: anyone who finds the URL spends the owner's quota. Its real protection is the hard caps (profile whitelist, ≤4 bands of 1–120 min, coordinates inside Brazil); the `Referer` check is weak and only filters casual use. ORS error bodies go to the function log, never to the browser, because they can echo the sent header.
    - Netlify cuts a synchronous function at 10 s, so the upstream fetch aborts at 9 s to return an explainable message instead of a raw 502.
    - **The ORS host moved.** `api.openrouteservice.org` was deprecated in April 2026, throttled to 10% of quota in August and shut down around 28/09/2026; the replacement is `api.heigit.org/openrouteservice`, **same key**. The function tries the current host and falls back to the legacy one **only** on a connection failure or 404/410 — a 401, 429 or 400 is a real answer and must be respected, not masked by a second call that would spend quota. This is what broke the live isochrone, and it had nothing to do with any release of ours.
    - `pintarLegendaIso()` is called **last in `aplicarIso()` and wrapped in try/catch**: the legend is an extra, and a browser where canvas is unavailable (hardened settings, anti-fingerprinting extension) would otherwise throw mid-function, land in `buscarIsocrona`'s catch and report a **network** failure for a working isochrone — the worst failure mode, because it blames the wrong thing.
- `tools/censo_uf.py` — builds one `censo/<cod>.json` from an IBGE sector-mesh GeoJSON plus the national income CSV, and updates the manifest.
- `tools/censo_pacote.py` — same output, but from a pre-joined "census radar" package (a `CD_SETOR -> {lat, lon, dom, mor, renda_*}` dict); emits one file per UF found, so a multi-state package needs one run. BA was built this way.
- `tools/municipios.json` — the 5,570 municipality names, so sector files do not depend on the mesh carrying `NM_MUN`.

None of `tools/` is served — `netlify.toml`'s command strips it.

Deployed to Netlify (project **maker-map**, `maker-map.netlify.app`) with continuous deployment from `main`: **merging to `main` publishes the live site automatically** (~1 min). There is no other release process.

### Publishing — standing authorization

The owner has authorized Claude to **publish without asking**: finish the work, open the PR, merge it, let Netlify deploy, then report what went live. Do not stop to ask "shall I merge?" — that question is already answered.

Two things this does **not** cover, because they are not publishing:

- destroying data or history (force-push over merged commits, deleting a user's stored projects, dropping a table);
- changing how people sign in, or what a plan unlocks for someone who is paying.

For those, ask.

**Review before publishing.** Whatever reaches `main` should first be checked by a dedicated reviewer pass (a subagent works well) focused on what would break production, not on style. This is not ceremony: the review before 2.1 found six defects, one of which meant the release did not deliver its headline feature — the new state was never fetched once the user moved the map centre. A syntax check alone would have passed it. Doc-only changes do not need this.

## Versioning — iOS-style

Releases are numbered and named the way Apple names iOS updates: `MAJOR.MINOR.PATCH`, where the third number exists **only** when the release is fixes-only.

| Form | When | Example |
|---|---|---|
| `X.0` | Big release: redesign, new subsystem, breaking change to saved projects | `2.0` |
| `X.Y` | New features / visible improvements — the normal case | `1.1`, `1.2` |
| `X.Y.Z` | **Only** bug fixes, no new features (Apple never adds features in a patch) | `1.1.1` |

Rules, all mirroring Apple's practice:

- **Never write `1.0.0`** — a release with no patch component is just `1.0`. The `.0` patch is implicit.
- **A patch never introduces a feature.** If a "fix" adds a control, a section, or a new behavior the user can reach, it is a `X.Y`, not a `X.Y.Z`.
- **Numbers only, no codenames.** iOS has no "Sequoia"; neither do we.
- Each release gets a **short title** in the release notes, plus the standard Apple opener: *"Esta atualização inclui os seguintes aprimoramentos e correções de erros:"* followed by bullets written for the user, not for a developer.

Where the version shows up:

- **PR title** — `Maker Map 1.1 — Legenda do raio e Raio do Mapa de renda`
- **`CHANGELOG.md`** — one section per version, newest first. Written in Portuguese, user-facing. Netlify strips `*.md` from the published output, so it never leaks to the site.
- **Git tag on `main` after the merge** — `git tag v1.1 && git push origin v1.1`
- Commit messages inside the branch stay descriptive as usual; the version lives on the release, not on every commit.

Decide the number **when opening the PR**: look at `CHANGELOG.md` for the last shipped version and bump according to the table above.

## Working on the code

Since it's a single-file app, use `Grep`/`Read` to navigate `app.html`. The file opens with a comment block (the "ÍNDICE DO ARQUIVO") that maps every subsystem to its function names — read it first; search by the term to jump to a section.

There is nothing to build/lint/test. The one meaningful check before committing is **JavaScript syntax of the inline `<script>` blocks**, since a syntax error silently breaks the whole page:

```bash
python3 - <<'PY'
import re, subprocess, tempfile, os
for f in ['index.html','app.html']:
    html=open(f,encoding='utf-8').read()
    for i,s in enumerate(re.findall(r'<script(?![^>]*\bsrc=)[^>]*>(.*?)</script>', html, re.S)):
        if not s.strip(): continue
        tf=tempfile.NamedTemporaryFile('w',suffix='.js',delete=False); tf.write(s); tf.close()
        r=subprocess.run(['node','--check',tf.name],capture_output=True,text=True); os.unlink(tf.name)
        print(f, i, 'OK' if r.returncode==0 else r.stderr)
PY
```

**The map cannot be exercised locally in this environment** — it needs a browser with internet, and auth needs the deployed Netlify site (see below). Verify changes by reasoning about the code and this syntax check; the user tests visually after deploy.

External hosts the deployed page depends on (relevant for CSP/network allowlists): `cdnjs.cloudflare.com` (MapLibre GL, JSZip), `tiles.openfreemap.org` (positron basemap style + tiles), `server.arcgisonline.com` (satellite raster), `fonts.googleapis.com`, `nominatim.openstreetmap.org` (address search), `api.bcb.gov.br` (IPCA series, Mapa de renda only). The isochrone adds **no** host to this list: the browser calls `/api/isocrona` on our own domain, and it's the Netlify function that talks to `api.openrouteservice.org`.

**This environment's proxy blocks** `ftp.ibge.gov.br`, `geoftp.ibge.gov.br`, `servicodados.ibge.gov.br` and `api.bcb.gov.br` (403 on CONNECT), so IBGE data must be uploaded by the user and the IPCA fetch had to be written to run in the visitor's browser. Netlify functions don't run here either, so the isochrone endpoint can only be exercised on the published site.

## Authentication (index.html ↔ app.html)

Auth is **Netlify Identity**, called directly over REST (`fetch` to `/.netlify/identity/*`) — no gotrue/widget library. Because of this:

- `index.html` is the gate: signup collects nome/sobrenome/telefone (stored in Identity `user_metadata`), and on login it stores the session in `localStorage` under **`makermap.user`**, then redirects to `app.html`.
- **The session is never stored without its `user`.** Without it `getUserPlano()` returns `free` and the storage key becomes `makermap.projetos.anon`: a paying user came back from the password-reset link with every Pro feature locked, their saved projects invisible, and anything saved afterwards going into an `anon` bucket shared with any other account in that browser. Both email-link flows (`/verify` for recovery and for signup confirmation) used to call `saveSession(tok, null)`. They now go through `sessaoComUsuario(tok)`, which takes the user from the token when gotrue includes it and otherwise fetches `GET /user` with the bearer; if neither works it stores **nothing** and sends the person to the login form with the password-already-changed / email-already-confirmed news. `loginFlow` passes a `{email}` fallback because there the email was just typed — a failed `/user` there degrades the plan but keeps the storage key.
- **The auto-redirect requires `s.user.email`, not just a token**, and lets a `#confirmation_token`/`#recovery_token` in the URL through first. Before, any `access_token` redirected: a session without a user went to the app, `app.html` only bounces back when `makermap.user` is *absent*, and the person was stuck in a degraded session with no way to reach the login form; and a logged-in visitor clicking a recovery link was redirected before `tratarHash()` ran, so the link did nothing. It deliberately does **not** check `expires_at` — the access token lasts an hour while the refresh token lasts far longer and `app.html` already renews with `grant_type=refresh_token`, so gating on it would sign everyone out hourly, a worse regression than the defect.
- `app.html` has a guard in `<head>` that redirects back to `index.html` if `makermap.user` is absent. This is a client-side gate, not edge security.
- **Identity must be enabled in the Netlify dashboard** and only works on the published site — `/.netlify/identity` does not exist when opening the file locally (`file://`) or on other hosts. Editing the user's own data uses `PUT /.netlify/identity/user` with the bearer token (with a refresh-token retry on 401).

## Two screens, one file

A left drawer (`#nav`, toggled by `#navBtn`, `body.nav-open`) switches between two screens, both living in `app.html`:

- **Mapa** — `#wrap`, everything described below.
- **Novos Negócios** — `#viewNeg`, a kanban of the areas.

`irPara(view)` flips `body.view-neg`, which `display:none`s the other screen. **Returning to Mapa must call `map.resize()`** (it does, twice — immediately and after the 280 ms nav transition), or MapLibre paints a blank canvas at the stale size.

They are one file, not two pages, so that going between the board and the map ("Ver no mapa") is instant and the board can tell live which of its deals are currently loaded on the map.

### Novos Negócios (kanban) — separate from Meus Projetos

**The two persistence systems are deliberately independent**, and merging them back would be a regression:

| | What it holds | Where | When it's written |
|---|---|---|---|
| **Meus Projetos** | the KMZs + map styling of one presentation map | `makermap.projetos.<email>` | only when the user clicks Salvar Projeto |
| **Novos Negocios** | the commercial pipeline | `makermap.negocios.<email>` | automatically, on every change |

So a card is **not** a `DATA` feature. It is its own record in `NEGOCIOS` (`{chave, nome, grupo, ha, haTxt, lat, lon, cor, status, valor, contato, obs, ts}`) — a copy of what the board needs, no geometry. Consequences, all intended:

- `negSincronizar(DATA.features)` runs after `integrarFeats` and creates the missing cards. It **only adds** — a deal never disappears because the map changed.
- Removing the KMZ (`excluirGrupo`) or "comecar do zero" (`limparProjetoAtual`) leaves the board untouched; the card just loses its `kb-flag` "no mapa" badge, computed live by `negNoMapa()`.
- Re-importing the same KMZ does not duplicate cards, because `negChave()` (`grupo|nome|lat(4)|lon(4)`) is stable across imports.
- Leaving the board is an explicit act — "Remover do quadro" in the card window.
- `carregarNegocios()` runs at startup, so the board is there without opening any project.
- `NEG_COLUNAS` is the column list; add to it and the board grows a column.
- Card fields come from KMZ files, so `esc()` escapes them before `innerHTML`. **Since 3.6 so does everything else that renders a KMZ name** — see "Escaping KMZ names" below; the board was simply the first place that got it right.
- Pro-gated as `novosNegocios`; the nav item itself is the gated element.
- One card per **area**, not per KMZ file: a KMZ carrying ten plots yields ten cards, since the plot is what gets offered and contracted.

## app.html architecture (the map)

`DATA` (a GeoJSON FeatureCollection of "glebas"/areas) **starts empty**; areas come only from KMZ upload or drawing. The map style is the OpenFreeMap **positron** vector style, recolored at load by `aplicarPaleta(style)`. `montarCamadas()` runs on the map `load` event and adds all custom sources/layers (`mascara`, `raio`, `glebas`, `satelite`) plus popups.

Key subsystems (all inside `app.html`):

- **Roads engine** — the most intricate part. `tierDe(id)` buckets road layers into macros (`rodovia`/`avenida`/`rua`); `subDe(id)` + `SUBVIAS` refine into sub-tiers (autoestrada/expressa/primária/…). `viaCfg` is keyed by **sub-tier** and drives `aplicarTierEstilo()` (color/width/opacity/contorno per sub) and `larguraFinal()`. `classificarTiers()` builds `viasTiers` (macro, for the above-mask stack) AND `viasSubTiers` (sub, for styling). `setSat()` swaps to the hybrid satellite look. **Base-map caveat:** positron only physically separates a few road layers (~motorway/major/minor), so `ajustarViasUI()` hides sub-tier controls that have no matching layer — most of the 7 sub-tiers legitimately don't appear.
- **Spotlight mask** — `construirMascara()` builds a world polygon with holes at the active glebas; `anelLimpo`/`anelOrientado` enforce correct winding.
- **Above-mask stack** — `ordemAcima` is the z-order of what's drawn over the veil; reordered by dragging rows in `#acimaLista` (`initDragAcima`/`sincronizarOrdemAcima`/`reordenarDOMAcima`), applied by `tierAcima()`/`aplicarPilhaAcima()`.
- **Design tokens (3.0)** — `:root` carries the whole scale, and new CSS is expected to use it instead of literals. Six text steps (`--fs-0`…`--fs-5`), plus `--fs-m` (8.5px, uppercase badge inside a cell — not reading) and two **display-number** steps (`--fs-n1`/`--fs-n2`) that sit outside the text scale on purpose, because the product is an image read from across a room. Three ink tones: `--ink` (body), `--ink-2` (control label), `--ink-3` (meta/supporting text — it exists so explanatory text stops competing with the control it explains). Base-4 spacing (`--sp-1`…`--sp-5`); `#editor` and the drawers both inset `--sp-4`. Functional colours come as ink/background/line triples (`--ok`, `--warn`, `--bad`, `--del`) plus one colour per analysis (`--c-renda`, `--c-iso`) shared with the map layers. **The body floor is `--fs-1` = 10.5px**; nothing in the product should be smaller except `--fs-0`/`--fs-m`.
- **Collapsible sections** — `<details>` is styled for `#editor` **and** `.side-drawer` (they are twin panels; it used to be editor-only). Every `<summary>` can carry a `.sm-val` on the right with the **value in force**, so collapsing never hides state — `syncResumoSecoes()` fills the Mapa de renda ones. Open/closed lives in `localStorage['makermap.secoes']` via `ligarSecoes()`, **not in the project**: it is a tool preference, and a 2024 project must not reopen with the 2024 layout (same precedent as `makermap.drawerW`). A plan-locked section neither restores nor records a preference, because `aplicarPlano()` forces `open=false` and that would survive the user subscribing. A section the *program* opens ("born open when there is work to do") goes through `secaoAbrirAuto()`, which marks the element with a `data-auto` attribute the listener skips — **not** a synchronous flag, because `<details>`'s `toggle` event is dispatched in a later task and the flag would already be cleared. Without that, the heuristic fired once per browser and stored a preference nobody expressed. The disclosure triangle is **drawn in CSS**, not the native `::marker`: `display:flex` on `<summary>` stops some engines from rendering it, and a closed section with no affordance reads as dead. `details:not(.e-info)` keeps the ⓘ primitive's own marker.
- **`.e-info`** — the progressive-disclosure primitive ("Como estes números são calculados", "O que é cada recorte", "Como funciona este quadro"). The label says what is inside, never "mais informações", and the text inside is **larger** than the footer prose it replaced. In `renderRenda()` its open state is kept in `rendaInfoAberto` because that panel's HTML is rebuilt on every repaint.
- **Editor UI** — `montarEditor()` builds every editor section (Por cidade, Por área, Mapa, Rótulos, Raio, Máscara, Vias, Sobre a máscara) and exposes `window.MakerMap.{coletar, aplicar}` (the styling-state serializer). Editor sections that render per-row use `*RowRefs` objects to sync inputs on reset/restore rather than DOM indexing. The editor is a resizable drawer (`--drawer-w` CSS var, drag handle `#edResize`, width persisted in `localStorage['makermap.drawerW']`).
- **Rótulos** — `lblCfg` + `classificarRotulos()` + `aplicarLbl()` style basemap labels per tier.
- **"Mapa" section** — `mapaCfg` + `camadasMapa(k)` toggle color/visibility of basemap layers (terreno, água, verde, divisas, aeroporto, áreas urbanas, construções) by `source-layer`.
- **Raio** — `gerarCirculo(km, centro)`/`atualizarRaio()` around `centroRaio`. Its map legend is a `symbol` layer (`raio-rotulo`) driven by `raioLbl` + `aplicarRaioLbl()`: free text (empty = the automatic "Centro · raio N km"), own color/size/halo, and an on/off independent from the `#chipRaio` group toggle — so every place that flips raio visibility must set only `raio-fill`/`raio-borda`/`raio-centro` and then call `aplicarRaioLbl()`.
- **Raio do Mapa de renda** — a **second, independent** circle living in the "Mapa de renda" drawer: state in `rendaRaio` (`{on, km, centro, cor, fill, lbl}`), source `raio-renda`, layers `raior-*`, applied by `atualizarRaioRenda()`/`aplicarRaioRenda()` and synced to the drawer inputs (`#rd*`) by `syncRaioRendaInputs()`. It shares nothing with the Edição raio except `gerarCirculo()`; picking its center on the map uses `pickCentroRenda` (mutually exclusive with `pickCentro`).
- **Censo IBGE 2022** — the income analysis inside that circle. Data is served **one file per state** (`censo/<cod>.json`), catalogued by `censo/manifest.json` (`{ufs:[{uf, cod, nome, arquivo, setores, bbox}]}`). `carregarCenso()` fetches the manifest once, then `censoUFsDoRaio()` picks the states whose bbox the circle reaches (bbox widened by the radius in degrees, so a neighbouring state clipped by the circle's edge still loads) and `censoAnexar()` merges each into `CENSO` (`{mun:{code:name}, s:[[lat,lon,cd_mun,dom,mor,renda_media,renda_mediana]]}`), resizing `censoDist` and invalidating `censoCache`. **Adding a state is adding a file plus a manifest line — no code changes**; `tools/censo_uf.py` (raw IBGE mesh + CSV) or `tools/censo_pacote.py` (pre-joined package) produces both.
    - Loaded today: **SP, MG, BA** — all three from the IBGE *malha preliminar* (polygons). Coverage against the sector count in the income CSV: SP 98,989/100,928 (1.9% missing), MG 49,924/50,929 (2.0%), BA 30,311/30,739 (1.4%). SP was originally built from *faces de logradouros* and was missing 10% (~964k households, mostly rural); the v3 package rebuilt it from polygons and recovered them — **do not regress to a faces-de-logradouros source**.
    - **Changing a state's data requires changing its filename** (`35.json` → `35-v2.json`, manifest `arquivo` updated). `netlify.toml` caches `/censo/*` for a day *without* `must-revalidate`, so a recent visitor would otherwise pair the new manifest (5-min cache) with the stale state file and see undercounted totals with no warning — `censoAnexar()` does not check `s.length` against the manifest's `setores`. The manifest is the indirection that makes this a one-line change.
    - Every state is audited against `Agregados_por_setores_renda_responsavel_BR.csv` before being accepted: per-sector income must match exactly (SP 89,968, MG 46,489, BA 27,845 sectors — zero discrepancies so far), municipality counts must equal the IBGE's (645/853/417), the bbox must match the state's real extent, and `mor` must vary per sector (a constant per municipality would mean a municipal average was pasted in). The whole country would be >6 MB gzipped, which is why it is never loaded at once. `censoStatus` gains `'fora'` for a radius outside every available state, which the panel reports by listing what *is* loaded rather than showing zeros.
    - **`carregarCenso()` must stay reachable after the first load.** Moving the centre or growing the radius can reach a state that was never fetched, so `atualizarRaioRenda()` calls it and the four callers guard on `censoStatus!=='carregando'` — **not** on `'vazio'`, which would freeze the loaded set at whatever the first load happened to need (and make `'fora'` a dead end the user could only escape with F5). `carregarCenso()` is cheap when nothing is missing.
    - `censoAnexar(cod, js)` refuses a UF already marked `'ok'`; appending twice would double households, population and the bracket distribution. Retries therefore clear only the non-`'ok'` entries of `censoUF`.
    - `censoNomesUF()` lists the whole manifest (for "the base covers"), `censoNomesCarregadas()` only what is in `CENSO` (for "these are loaded") — conflating them made the panel claim a state was covered while showing zeros.
    - A partial network failure keeps `censoStatus==='ok'` but `censoUFsFaltando()` drives a red banner naming the missing states, because presenting a radius total with one state silently absent is a confidently wrong number. `censoConsulta(lat, lon, km)` scans all sectors with Haversine, caching distances in a reused `Float32Array`, and aggregates **weighting by `dom`** — a plain mean across sectors would let a 10-household sector count as much as a 500-household one. `renderRenda()` paints the drawer panel; `censoCache` keys on `km|lon|lat` so redraws don't recompute. **A slice where the IBGE withheld income for every sector (`q.faixaTot === 0`) prints no income at all** — not `R$ 0` with class "E", which is a confident wrong number over tens of thousands of real households. It is not a rare shape: 244 sectors and 43,852 households inside a 3 km radius in Campinas are like this. The panel says so and keeps the household and population totals, which still hold; the bracket chart is suppressed, since it would be seven rows of "0,0% (0)".
  - **"Renda mediana" is a real weighted median (3.6).** It used to be the household-weighted **mean** of the per-sector medians, under a label that said median — and since income is right-skewed it erred **upward, always**: Campinas 10 km printed 6,329 against a true 4,500 (+40.6%), Ribeirão +38.4%, a 100 km radius from the Sé +57.8%. It now sorts the per-sector medians and accumulates `dom` to half of `domRenda`. The **mean still uses the full value** and the brackets are still decided over `Math.round(rm)` — both pre-existing rules explained above, and breaking either makes the chart disagree with the map's colour. The label did not change (word-for-word contract with the spreadsheet); the ⓘ and the spreadsheet's MÉTODO now say it is a median *across the slice's sectors, weighted by households*, because a median of sector medians is not the true household median and the panel must not imply it is. Verified by execution over 198 slices of SP: `mediana <= média` in 100% of them, and the value is always one actually present in the slice.
  - **Partial coverage of the slice is announced (3.6, `censoGrade`/`censoCoberturaPct`/`q.cobertura`).** The base covers SP/MG/BA; a radius centred inside one of them whose *area* reaches PR, MS, GO, RJ… counted only the covered households and divided by the **whole** circle. Presidente Epitácio at 30 km had 57% of its area with data; a 500 km radius from the Sé printed 20,058,352 households and "25.54/km²" with not a word. There was a banner for a manifest state that failed to load and one for a centre outside everything (`'fora'`) — nothing for the common case. **Bounding boxes do not work here**: SP's bbox swallows chunks of MS, PR and MG, and scores 100% on every case above, so a bbox test would be a banner that never fires where it matters. Instead `censoGradeMontar()` builds a `Set` of occupied 0.05° cells (~5.5 km, 23,205 cells for 179,224 sectors, 35 ms), and `censoCoberturaPct()` samples the slice on a 40×40 grid counting points with an occupied cell within **±2 cells**. `±2` is the only value that separates the acceptance sets — ±1 makes the fully-covered Bahian sertão and Barreiras cry wolf (huge sectors), ±3 silences Ourinhos; **do not touch it without redoing the 9-must-warn / 23-must-stay-quiet table**. `q.cobertura` lives inside `q` so it enters `censoCache` and panel and spreadsheet read the same number, and `censoAnexar()` nulls `censoGrade` on the same line it nulls `censoCache.chave` — otherwise the banner sticks to a stale set of states. The measure **overstates** coverage (83% where the fine measure says 57%), which is why the sentence says "ao menos N% …" and the spreadsheet cell is labelled "no máximo" and only appears when there is something to warn about. The bold clause says the area "está sem setor censitário", not that the base fails to cover it: on a coastal slice the cause is the sea, and both dilute the density the same way but only one is our fault.
  - **The radius cut is by sector centroid**, so a sector straddling the circle counts fully in or fully out. `censoConsulta` therefore also returns `margem`: the share of households living within one local sector-radius (`rs = km/√n`) of the circle's edge — an upper bound on that error. Tiers: ≤5% silent, 5–15% warning, >15% (or fewer than 30 sectors) "radius too small, don't use these numbers". This is why very small radii are unusable: at 500 m in central São Paulo the edge band holds more households than the radius itself.
  - **Map layers** — `censoCamadas(q)` fills source `censo` with **every** sector inside the radius and drives three layers off it, all above the veil and below the `raior-*` circle so the dashed outline stays readable. All require the radius to be on; points and heat can be on together.
    - **Sectors without income are excluded by a layer `filter`, never by leaving them out of the source.** `censo-pts` and `censo-surf` carry `filter:['>',['get','renda'],0]`; `censo-heat` deliberately has none, because density is people living somewhere and a sector the IBGE withholds income for still has households. Filtering at the source (as this did until 2.2.1) made the density heat draw fewer households than the panel counted — 17% fewer in Campinas once SP moved to polygons, where 9.1% of sectors have no income figure.
    - `censo-pts` (`rendaRaio.pts`, chip `#chipCensoPts`) — one circle per sector, coloured by income bracket. `censoStepCor()` builds the `step` expression from `censoCores()`, whose stops mirror `censoFaixaIdx()` exactly (both "less than"), so the map colour always matches the bracket the household was counted in. **That only holds because `censoAgregar()` assigns the bracket over `Math.round(rm)`** — the same rounded value `censoCamadas()` writes into the `renda` property the `step` reads. Deciding over the full value put a sector in one bracket in the chart and another colour on the map: at the default factor 1.5 (demais moradores 50%), an income of 3,333 gives 4,999.5 — counted in "3.000 a 5.000", painted as "5.000 a 8.000". It was 31 sectors and 4,957 households across SP+MG+BA. The **weighted mean keeps the full value**; rounding each sector before weighting would bias the money. Verified by execution over all 179,224 sectors at seven factors: zero disagreements. The **same colours paint the drawer's distribution bars**, so that chart doubles as the legend — and each bar's swatch is an `input[type=color]`, making the legend the editor. Custom colours live in `rendaRaio.cores` (`null` = default) and save with the project; two presets are offered, `CENSO_CORES_PADRAO` (traffic-light, the default) and `CENSO_CORES_SEGURA` (YlOrBr, monotonic lightness, the only one that survives greyscale printing and red-green colour blindness). The swatch `oninput` deliberately does **not** call `renderRenda()` — rebuilding the HTML would close the browser's colour picker mid-drag; it repaints the map and patches the one bar instead.
    - `censo-surf` (`rendaRaio.heat` + `heatModo:'renda'`) — the income "heat": big blurred circles carrying the bracket colour, which merge into a smooth surface. **Deliberately not a `heatmap` layer** — heatmap sums weights, so weighting by income would conflate "many households" with "high income". This is a visual smoothing of income, not a density.
    - `censo-heat` (`heatModo:'dens'`) — the real density heatmap (native `heatmap` type), weight = `dom` saturating at 600, ramp `CENSO_HEAT_CORES` (cool→warm, deliberately unlike the income ramp so the two maps don't look alike).

    - `rendaRaio.ipca` (default on) — `carregarIPCA()` fetches **BCB SGS series 433** (IPCA % per month) *in the user's browser* and compounds from **August/2022** (July's own variation is already inside the 31/07/2022 reference) up to **two months before today** (IPCA for month M is published ~the 10th of M+1, so two months is always available). **There is deliberately no baked-in fallback table**: inventing inflation indices would produce confident, wrong money. On failure the panel says so and shows July/2022 values.

The panel footer **always states which of the two is in force**, so nobody reading the analysis has to guess where the money's base came from. This does **not** relax the no-invented-index rule: the program still never makes one up — the user declares one, and the footer says so.
    - **`fonteCorrecao()` is the single authority on which correction won** (`off` / `manual` / `bcb` / `nenhuma`), and both `fatorRenda()` (the number) and `censoBaseTxt()` (the sentence that announces it) read from it. They must agree, and while the precedence rule was written in two places they did not: the panel's "Base dos valores" line announced July/2022 while the figures were already corrected by the typed percentage — the panel contradicting itself about money, and erring upward. `censoBaseTxt()`/`censoQuemTxt()` are also what the **sector popup** uses; it used to hardcode `jul/2022 · responsável` over values `censoCamadas()` had already multiplied by `fatorRenda()`. `pctTxt()` is the one formatter, after the same 20 printed as "+20%" and "+20,0%" in the same panel. **`censoPremissas()` (3.0) is the third reader** — it returns the Moeda/Correção/Renda(/Tempos) label-value pairs for the `.rd-prem` band that **replaced** the "Base dos valores" row. Its rule: the Moeda cell says `R$ jul/2022` **exactly when the monetary factor is 1**; on the typed-percentage path there is no month to name (the user declared a percentage, not a date), so it says "R$ corrigido" and the number goes in the cell beside it, and a typed 0% really is July/2022. Verified by execution across 336 states that the factor, the band and the popup sentence never disagree about whether a correction was applied, and that "sem trânsito" shows up exactly in isochrone mode.
    - **`carregarIPCA()`'s success handler repaints inside its own try/catch.** The `.catch` at the end of the chain is downstream of the success path, so a throw while repainting would overwrite `'ok'` with `'erro'` and the panel would say "indisponível" with a perfectly good series in hand — blaming BCB for a UI defect of ours. Same class as `pintarLegendaIso()`.
    - `rendaRaio.outros` (default 50) — percentage the other residents add to the head's income, so 50% means household income = 1.5× the head's. It is the **user's estimate**, not census data, and the footer says so.
  - Raw values in `CENSO.s` are never mutated; the factor is applied on read.
  - Numbers are **nominal R$ of July 2022** before adjustment, and the census income is the **household head's only**. The panel footer always states which currency month the figures are in and whether the household estimate is on.

- **Scroll zoom speed (3.4)** — `ZOOM_VEL` (`{lento:0.25, medio:0.5, rapido:1}`) is a **factor over both of MapLibre's rates**, applied by `aplicarZoomVel()` through `map.scrollZoom.setZoomRate()`/`setWheelZoomRate()`; the three-step segmented control lives in Configurações (`#cfgZoomSeg`) and the choice in `localStorage['makermap.zoom']` — a tool preference, same precedent as `makermap.export`.

    - **The ruler is validated before anything is measured with it.** `scratchpad/daltonismo/cvd.js` implements the Machado, Oliveira & Fernandes (2009) simulation matrices (protanopia/deuteranopia/tritanopia at severity 1.0 — full dichromacy, so designing for it covers the far more common partial forms) applied in **linear** RGB, plus CIEDE2000. `ferida.js` checks it against the 23 published pairs of Sharma, Wu & Dalal (2005) — worst error 4.2e-5 — and against behaviour that *defines* each condition (red and green collapse in protan/deutan, blue–yellow survives there and collapses in tritan, neutrals never move). A wrong simulator produces a palette that looks verified and is not. On the first run one pair failed; the error was **my transcription of the reference table**, not the code, and 22 pairs matching to 2e-4 while the 23rd returned a published value to four decimals is what showed which side was wrong.
    - **`POOL_CORES` was the real defect, and it was severe.** The city/plot colour cycle is *categorical*: no order, so any pair can end up adjacent, and the set's score is its closest pair. Measured: `#8B5CF6`/`#D946EF` at **ΔE 1.3** under protanopia — indistinguishable — and only 13.4 even in normal vision; nine of ten colours in some bad pair; **broken from the fourth city of a project**. The product's deliverable is a presentation map with one colour per city.
    - The replacement's first six are **Okabe & Ito (2008)**, the reference CVD-safe qualitative set; two of its eight are unusable here (its yellow `#F0E442` vanishes on light backgrounds and its black on dark, and the product has nine light and four dark palettes). The last four come from search, entering through the channel a dichromat does **not** lose — lightness. **Ordered by prefix**, because `proximaCor()` serves the list in order: a three-city project gets the three most separated colours in the set, not three from an arrangement optimised for ten. Worst pair: ΔE 19.9 at three cities, 12.5 at four, **11.1 at ten** — and 11.1 is Okabe–Ito's own floor, so the extension degrades nothing.
    - **A blind search scored better and was rejected, deliberately.** It reached ΔE 12.7 at ten (and 38.0 at four) but returned four greens and five magentas. Three reasons the metric lost: CIEDE2000 was fitted on *normal* vision, so applying it to simulated dichromat images is an unvalidated extrapolation, while Okabe–Ito was tested with actual dichromats; a broker has to say "the green one" out loud over a presentation map, and five mauves are not nameable; and most readers see normally, for whom lime-next-to-green-next-to-dark-green is a bad map. **The metric informs, it does not decide** — and that override is written down rather than hidden behind the numbers.

The outline is where identity lives; the 32% wash falls to **ΔE 2.9 at ten cities** on a light background, so the large area is nearly uninformative at that count and the harness asserts the opacity it measured against. Every colour also has to *appear* on both the lightest and darkest basemap in use (floor 1.8:1 against each) — `#CAB0AF` sits at 1.85 on light and the two dark derived ones at 1.87/1.88, tight but passing.
    - **The `daltonismo` basemap palette carries meaning by lightness, on one hue axis.** Blue–orange, which is what survives protan and deuteranopia; no information-bearing pair is red–green, and the harness fails on any saturated red in the palette. Its 16 obligatory pairs each have their own floor and are checked across all four visions; the tightest is park label vs road label (ΔE 8.3 under deuteranopia, floor 8). The two greens came from search because they are **squeezed** between the light urban blocks and the edge of still looking like vegetation — moving away from one approached the other. The first search maximised separation and returned L\*66/L\*56: dark patches on an L\*95 background, against the product's own rule that the basemap is context, not subject (the same rule the building follows). The objective became "1.35× margin on the floors, then the lightest that passes"; the shipped pair has 1.41×.

Verified by execution that circle and polygon return the same aggregate for the same sector set.
    - **The edge margin was rebuilt for polygons.** `rs = km/√n` comes from "circle area ÷ n sectors" and means nothing on an irregular outline. `censoConsultaPoly` derives `rs` from the polygon's real area (`areaPoligonoKm2`, shoelace in degrees converted by mean latitude) and measures the band against the outline via `censoBordaPoly`. That one is **deliberately approximate**: it measures distance to the outline's *vertices*, not its segments, through a grid of cell size `rs` — the routing polygon has a vertex every few hundred metres, the margin is an upper bound rather than an exact measure, and segment-exact would be ~10⁸ operations per redraw.
    - `rendaAtivo()` replaced the direct `rendaRaio.on` tests, which now only cover one of the two modes. `censoCaixaAtual()` generalised the UF-selection box. The cache key carries the mode (`'i|calcEm|faixaSel|fator'` vs `'r|km|lon|lat|fator'`), since the polygon only changes when recalculated.
    - The drawer's circle keeps its own on/off independent of the mode, so both geometries can be drawn at once for comparison; only the analysis follows `rendaModo`.
    - Restoring a project with `rendaModo:'iso'` but no polygon falls back to `'raio'` — the mode would otherwise be a dead end.
- **Side drawers** — Salvar Projeto, Meus Projetos, Cores, Mapa de renda, Isócrona, Exportar imagem and Exportar dados open as right-side drawers (`.side-drawer`, `#wrap.side-open`) via `abrirGaveta(id)`/`fecharGaveta()`, mirroring the Edição drawer. One open at a time; opening any closes the editor and vice-versa. "Mapa de renda" (`#btnRenda`) is Pro-gated. Editor-style rows reused inside a drawer go in a `.sd-sec` wrapper (zeroes their horizontal padding, since the drawer already pads). Compass on the map: `NavigationControl({showCompass:true})`. `abrirGaveta`/`fecharGaveta`/`abrirEdicao(true)` all route through `marcarChipGaveta()`, which marks the opening chip `.aberta` — before 3.0 nothing on screen said which of the drawers was open.
  - **The Mapa de renda drawer's order is its content** (3.0): ① layers · ② slice (the `Raio|Isócrona` segmented control **and** the active mode's parameter on the same line — km, or the two times) · ③ `#rendaAnalise`, the answer · then ④–⑧ as `<details>`: Isócrona parameters, Ajuste dos valores, Mapa de calor, Legenda no mapa, Aparência do raio. The answer used to start ~870px down, a screen below the controls that feed it, and the use is a loop adjust→read→adjust. Two sections open themselves **once** when there is work to do (`rendaIsoBox` when the mode is iso with no polygon; `heatOps` the first time the Calor chip goes on) and the stored preference governs afterwards.
- **Repeated UI blocks are generated, not copied (3.0)** — `montarBlocosRepetidos()` fills every `[data-mm-ct]` with `blocoCentroHTML()` and every `[data-mm-leg]` with `linhaLegendaHTML()`, **using exactly the ids that existed before** (`edCt*`, `rdCt*`, `riCt*`, `isoCt*`, `edRaioLbl*`, `rdLbl*`, `isoLbl*`), so no handler, no sync function and no saved project changed. It runs **before** `montarEditor()` and before every handler is attached — that order matters. The center field accepts an address **or** a pasted `lat, lon`: `coordsDoTexto()` is the single parser (it handles the ambiguous decimal separator), and `ctInstalarAtalhoCoords()` wraps each of the four existing search handlers **at the end of the file**, because it captures their `onclick` and cannot run before they exist. `ctSync(pfx)` repaints the read-out line from the number inputs, which stay the source of truth. `pickMarcarBotao()` marks the ⌖ button while a click mode is armed.

## Projects & persistence

`coletarEstado()`/`aplicarEstado()` capture and restore the **styling** state; the **project** system (`coletarProjeto`/`carregarProjeto`/`limparProjetoAtual`) additionally snapshots the full `DATA`/`labelPts`/`grupos`/`CORES` and stores named projects per user in `localStorage['makermap.projetos.<email>']`. **Each session starts blank** — there is no auto-restore; users open a saved project manually via the "Meus Projetos" header menu. `resetPadrao()` returns everything to defaults. When a change alters the shape of a persisted structure (e.g. the roads move from 3 macros to 7 sub-tiers), older saved projects fall back to defaults for that part rather than breaking.

All user data (drawings, KMZ, projects, edits) lives **only in the visitor's browser** — nothing but the Identity auth calls leaves the client.
